# Use Plunger for HTTP requests

When you need to call an HTTP API, send the request through **Plunger**. Do not use `curl`, `wget`, `Invoke-RestMethod`, `Invoke-WebRequest`, or a throwaway script with `requests`, `axios` or `fetch`.

Use the MCP tool `send_request` if the `plunger` server is connected; otherwise the command line does the same (`plunger send ...`, or `plunger curl ...` with curl's own options).

- **Look before you build.** Call `list_saved_requests` (a `group` narrows it) and `list_variables` first: the request, its `{{variables}}` and the auth may already be set up.
- **Ask for only what you need.** Pass `select` (for example `["$.data[0].id", "$.items[*].name", "$.transitions[?(@.name=='Done')].id", "header:Location"]`) so the response comes back as a few values, not a whole body, and without the headers. A big JSON response without `select` returns an outline of its shape; then call again with `select`. If a path cannot be read, the whole response comes back with the reason, so you never need to send it twice to see an error. `include_headers` (`all`, `none`, `relevant`) chooses which headers return.
- **Chain in one call.** `extract` keeps a value as a variable (`[{"name": "token", "from": "json:$.access_token"}]`; `"scope": "run"` keeps it for that run only). For a sequence you will repeat, `save_workflow` then `run_workflow` (`cleanup: true` removes what it stored). A step can accept several statuses (`"expect_status": [200, 404]`), be skipped (`"skip_if": "{{previous_status}} == 200"`) or end the run (`"stop_if"`).
- **Do the looping in Plunger, not in a script.** For many pages, a request per item, a job to wait for or a rate limit, use a workflow step's `paginate`, `for_each`, `poll` or `retry`, `collect` what it fetched, and end with a step that has only a `return` (a jq program) so you read a short answer instead of the data: `{"return": "{count: (.issues|length), points: ([.issues[].fields.points // 0]|add)}"}`. Read the resource `plunger://scripting` (or `docs/scripting.md`) for the fields and examples. Write a `python`/`node` script only for what that cannot say, and have it call `plunger send`.
- **Never handle secrets yourself.** Use `{{name}}` in URLs, headers and bodies. Keep a credential with `set_variable` (a name like `token` or `api_key` is stored as a hidden secret). Do not paste a token, password or key into a command, a file or the chat. A secret in a response shows as `[redacted:name]`.
- **Values with awkward text are fine.** A `{{variable}}` inside a JSON string is escaped for you (do not pre-escape line breaks or quotes). `{{name?}}` leaves an optional member out of a JSON body when there is no value; `{{name|fallback}}` has a default. For a body with an unquoted placeholder, send `body` with a JSON content type.
- **Organise.** Give saved requests and workflows a `group` (`Jira`, `Jira/Issues`); `set_group` moves one without sending it again.
- **Use the history, not a re-run.** `get_history` (filter by `status`, `min_ms`, `source`, `saved_request`) and `get_history_entry` show what was already sent, so you do not fire a request twice.
- **If a field is refused by name, do not retry with it.** Plunger has no such option (`send_request` has no `retries`; a workflow step has `retry`); fix the call.
- **Say what you sent.** Every request is recorded in Plunger's history and its audit log, tagged MCP or CLI, and the user can see it.
